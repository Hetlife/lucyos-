# TR-1-07 — Guard: bridge messages that are not LucyOS commands must not become tasks

**Why:** The `lucy:` marker is an instruction to an AI agent, and agents misjudge. A code-level guard makes chatter harmless (ISSUE-038).
**Current evidence:** `router.handle` files any unrecognised text as an INBOX task; the OpenClaw bridge forwarded "pulled" and created `TASK-77EAD62D`.
**Executor:** CLAUDE_CODE (Fable override for `aion_core/router.py` recorded first; or done entirely in `cli.py` if a public `router.recognises(text)` is added)
**Scope:** for `--channel openclaw` only: if the text matches none of the router's commands, reply "Not a LucyOS command. Nothing was saved. Use `lucy: help`." and do not file a task. Direct-bridge and PWA behaviour (quick capture into INBOX) stays unchanged. Tests: recognised commands still route; unrecognised text creates no task and no `whatsapp.in` event body; existing capture behaviour on other channels unchanged.
**Do not touch:** `.lucy/authority/**`, verifier, CI workflow; the strict `APPROVE`/`DENY` grammar; no new module or dependency
**Dependencies:** TR-1-05 evidence (so the guard is judged against the observed behaviour)

## Steps
1. Add a pure `recognises(text) -> bool` next to `handle` that reuses the same patterns (single source of truth; `handle` calls it).
2. In the bridge path of `cli.py`, refuse to route when `recognises` is false; still log the bridge event with verb `other`.
3. Tests as above; full gates.

## Acceptance tests
- `lucyosctl whatsapp "pulled"` creates no task and returns the not-a-command reply
- `lucyosctl whatsapp "status"` unchanged
