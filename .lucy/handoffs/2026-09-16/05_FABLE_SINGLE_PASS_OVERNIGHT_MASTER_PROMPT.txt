OWNER DECISIONS / NEW INVARIANTS TO INCORPORATE

1. REPOSITORY VISIBILITY
LucyOS may remain public temporarily until the Mac migration/setup is complete. Therefore assume everything committed to GitHub is public. Never commit credentials, private Drive content, customer data, raw sensitive logs, OAuth material, machine secrets, or private operating data. Do not change repository visibility tonight.

2. CURRENT COMPUTE ROLE
Mark-2 is a Linux test bench/rehearsal machine, not the final permanent host. A local Linux PC may become available for additional tests in about two days. The planned Mac controller is 24 GB unified memory, not 64 GB.

3. CROSS-PLATFORM IS A PROTECTED ARCHITECTURAL INVARIANT
LucyOS must remain one codebase that can run on macOS and Linux without forking core logic.
- Core/domain/AION logic must not directly depend on systemd, launchd, Linux-only paths, or macOS-only paths.
- OS-specific concerns belong behind a small platform/host adapter layer.
- Linux and macOS service definitions, path resolution, process/service management, bootstrap, permissions probes, and platform quirks must be isolated.
- CI must enforce portability where practical.
- Future Linux machines with more RAM must be able to run the same LucyOS brain and project state.
- Do not duplicate business logic between Linux and macOS adapters.
Encode this invariant durably in architecture docs/contracts and, where appropriate, in machine-checkable tests/guards before bulk implementation.

4. LOCAL-FIRST DRIVE / FILE SYNC
Do NOT make Mark-2 dependent on writing directly to Google Drive. Current Mark-2 Drive reads work but writes are not a requirement for tonight.
Target model:
- Mark-2 and future hosts maintain a local working mirror/cache/staging tree.
- All local work continues even if Drive is unavailable.
- Outbound Drive changes become deterministic `PENDING_SYNC` artifacts/ledger entries.
- A trusted external connector/chat/app with Drive write access may promote/sync those artifacts later.
- Drive is collaboration/backup transport, never Lucy's transactional source of truth.
- Do not spend tonight fixing OAuth or forcing Mark-2 uploads.
Design the local mirror, pending-sync ledger, idempotency, conflict policy, and provenance cleanly. Avoid building a second database.

5. SHARED INTELLIGENCE LIBRARY / DATA ASSET
LucyOS is a multi-project / multi-company platform. For now the owner wants maximum cross-project learning rather than strict silos, but every datum must carry provenance and project/ownership metadata so stricter separation can be added later without a data migration crisis.

Create/confirm a canonical data-intake contract:
- preserve raw originals immutably;
- normalize useful text to UTF-8 / structured JSON or JSONL where appropriate;
- normalize analytical/tabular data to CSV/Parquet or another justified machine-readable format; Excel is an import/export/view surface, not canonical truth;
- attach source, acquisition timestamp, project/company, entity references, schema/version, confidentiality/permission tag, transformation history, checksum/content hash, and training-eligibility metadata;
- raw evidence, normalized records, derived signals, curated training sets, indexes, and exports must be distinguishable;
- vector/embedding indexes are disposable/rebuildable, never canonical memory;
- use deterministic filters/exact lookup/SQLite FTS before semantic/vector retrieval;
- a local recall/indexing service should let local/Ollama models retrieve small relevant slices so paid models do not scan the library;
- design for future NAS/cold-storage migration and rebuildable indexes.
Do not build a large vector infrastructure merely because it is fashionable.

6. LUCY / OPENCLAW / FUTURE LUCY CLAW
Near-term interaction model:
OWNER -> OpenClaw interactive runtime -> Lucy Bridge -> AION/LucyOS canonical state/tools.
OpenClaw can provide chat/model/plugin runtime initially, but it is replaceable. LucyOS owns canonical state, projects, tasks, approvals, memory, provenance, budgets, policy and durable knowledge.

Preserve a model/provider gateway seam inside LucyOS so future direct provider APIs can be added without rewriting projects.

Future runway: `Lucy Claw` may become a thin, upstream-compatible OpenClaw-derived distribution/plugin bundle customized for Lucy. Do NOT start a heavy fork tonight. Prefer supported plugin/adapter surfaces and keep an upstream-compatible boundary. The failure of OpenClaw upstream must not destroy LucyOS: pin known-good versions, preserve a reproducible copy/mirror strategy, and keep Lucy state outside OpenClaw.

7. MULTI-PROJECT / REUSABLE CAPABILITY MODEL
LucyOS is the platform. Companies/projects (e.g. SevaaConnect, Strategy Factory, future real-estate/import-export ventures) consume reusable capabilities, skills, schemas and teams.
- Shared capabilities should be reusable across projects.
- Project/company context and data provenance remain explicit.
- A new company should start from reusable capabilities rather than cloning an entire agent stack.
- Prefer skills/services/workflows over permanent agent proliferation.

8. HR / TEMPORARY WORKER MODEL
Lucy is the owner-facing supervisor. Team supervisors/HR logic may request temporary workers when workload spikes.
- Lucy may create bounded temporary workers automatically inside approved budgets/capabilities.
- Temporary workers inherit least-privilege task scopes and terminate cleanly after the task/TTL.
- Permanent new roles, privileged/high-authority agents, new external credentials, material spend, or authority expansion remain owner-gated.
- More workers must not be treated as evidence of progress; throughput and verified outcomes matter.

9. PROGRESSIVE AUTONOMY / DEPLOYMENT GUARDIAN
Use progressive autonomy, not manual approval for every safe action and not unrestricted autonomy.
GREEN: reversible, bounded, policy-compliant work may proceed automatically.
AMBER: allowed only inside explicit standing scope/budget; otherwise request approval.
RED: fresh owner authorization.

Lucy may eventually auto-deploy GREEN changes only through a deterministic deployment guardian:
SNAPSHOT -> ISOLATE/SANDBOX -> IMPLEMENT -> TEST -> STATIC/SECURITY CHECK -> INDEPENDENT VERIFY -> STAGE -> HEALTH CHECK -> LIMITED DEPLOY -> MONITOR -> AUTO-ROLLBACK ON FAILURE -> EVIDENCE.
No process exit code alone counts as proof. Blast-radius limits, rollback, checkpoints, kill switch, audit trail and failure injection are mandatory before expanding autonomy.

Design the escalation subsystem now; do not buy or configure a telephony provider tonight unless already authorized.
Target policy:

- Urgent action-required event -> concise text/push first containing trigger, evidence, risk, exact approval/action, rollback and deadline.
