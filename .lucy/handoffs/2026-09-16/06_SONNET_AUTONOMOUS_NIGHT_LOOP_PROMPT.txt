NIGHT LOOP
Repeat this loop until the STOP CONDITIONS are met.

STEP 0 — REFRESH TRUTH
- Fetch latest remote refs.
- Read the current Fable queue and baseline again if either changed.
- Confirm the integration branch SHA.
- Confirm working tree is clean before starting a task.
- Never assume the previous task's base is still current.

STEP 1 — SELECT THE NEXT TASK
From `.lucy/execution/SONNET_TASK_QUEUE.md`, choose the highest-priority task that satisfies ALL of:
- intended for Sonnet/cheap model/local implementation;
- dependencies are already present on the current integration branch;
- task is not waiting for an owner merge/approval/hardware/external credential;
- allowed and forbidden paths are explicit;
- acceptance criteria/tests are explicit;
- no unresolved Fable architectural question remains.

Prefer independent tasks first so work continues overnight even while sequential PRs await owner merges.

If one task is blocked, record the blocker and immediately evaluate the next independent task. Do not repeatedly burn tokens retrying the same known blocker.

STEP 2 — BASELINE BEFORE EDITING
Create/update the task branch from the current integration base exactly as the queue specifies.
Before changing code, run the task's VERIFIED START STATE plus the standard baseline:
`python3 -m unittest discover -s tests -t . -q`
`./aion scan .`
If the start state no longer matches, STOP that task and mark `BLOCKED_START_STATE_DRIFT`; do not guess.

STEP 3 — IMPLEMENT ONLY THE WORK ORDER
- Touch only files/paths explicitly allowed by the task.
- Make the smallest maintainable change that satisfies acceptance criteria.
- Preserve working architecture before replacing anything.
- Use deterministic code/tests over prompt rules where possible.
- Reuse existing primitives instead of adding duplicate frameworks.
- Keep Linux/macOS portability invariant intact.
- Keep Mark-2/local file work local-first; do not make Drive writes a prerequisite.
- Do not add expensive model/API calls when deterministic/local logic can solve the problem.

STEP 4 — TEST IN LAYERS
Run, at minimum:
1. task-specific tests;
2. full test suite;
3. `./aion scan .`;
4. any migration/upgrade test required by the task;
5. authority verification required by the queue;
6. architecture anti-duplication verification required by the queue.

If the task concerns portability, also run all available platform-neutral tests and let CI provide macOS/Linux evidence.
If the task concerns recovery, prove restore/resume with a fresh process/state, not only mocks.
If the task concerns a background loop/service, prove clean start, stop, restart and idempotency where feasible.

Never hide, skip or `continue-on-error` a required failure merely to make the task appear complete.

STEP 5 — SELF-REVIEW BEFORE COMMIT
Check:
- Did I touch a protected file without explicit override?
- Did I alter architecture instead of implementing it?
- Did I add a duplicate control plane?
- Did I introduce Linux-only behavior into core logic or macOS-only behavior into core logic?
- Did I expose secrets, absolute private paths or sensitive logs?
- Did I add hidden network/API/spend behavior?
- Can the change be rolled back cleanly?
- Do tests actually prove the stated behavior?
If any answer is unsafe/unclear, stop the task and escalate.

STEP 6 — COMMIT / PR
Commit title:
`<TASK_ID>: <concise change>`
Include trailer:
`Task-ID: <TASK_ID>`
Push the task branch and open/update a PR into the integration branch.
PR body must include:
- task ID;
- exact base SHA;
- files changed;
- tests run + results;
- CI status if available;
- authority/anti-dup result;
- known limitations;
- rollback method;
- whether owner/Fable action is required.
Do NOT merge.

STEP 7 — VERIFY REMOTE CI
If CI runs automatically, inspect the actual job/check results.
- Green required checks = evidence.
- A red check is information, not permission to weaken a gate.
- If a failure is clearly mechanical and within task scope, fix it on the same task branch and rerun.
- If the failure requires architecture/protected-path/policy changes, mark the task blocked and escalate.

STEP 8 — CHECKPOINT
After each task, preserve a compact checkpoint in the safest available durable surface:
- Prefer the task PR body/comments and normal commit history.
- If Fable has designated a canonical night-progress file and the task permits updating it, update that file.
- Otherwise use local `$AION_HOME`/workspace checkpoint state; do not violate task path restrictions just to write a progress file.
The checkpoint must state task, branch, SHA, PR, evidence, status, blocker (if any), and next eligible task.

STEP 9 — CONTINUE
Return to STEP 0 and take the next eligible low-token task.
Do not wait for the owner if useful independent READY tasks remain.
Do not use a high-cost model merely because a task is tedious.
